# AboutIAM High-Density Q&A RAG Index
This file contains pre-compiled, structured Q&A pairs representing the core concepts, standards, and playbooks of AboutIAM, optimized for semantic RAG answer retrieval.

## Section 1: Identity & Access Management Glossary Q&A

Question: What is AAA (Authentication, Authorization, and Accounting) in Identity Security?
Answer: Analogy: The master security system of an apartment building: 1. Authentication checks your key at the front door. 2. Authorization checks if your key card unlocks the gym. 3. Accounting logs the exact time you entered and left the gym. Technical Specification: An architectural security framework. Authentication verifies a client's identity; Authorization determines permitted actions; Accounting monitors active resource usages and session durations for auditing and billing. More details: https://www.aboutiam.com/encyclopedia/?term=aaa

Question: What is ABAC (Attribute-Based Access Control) in Identity Security?
Answer: Analogy: Like getting into a VIP club only if you are wearing red shoes (a user attribute), it is before midnight (an environment attribute), and the club isn't full (a resource attribute). Your actual name doesn't matter. Technical Specification: An advanced access paradigm granting rights dynamically by combining policies against user attributes, environmental contexts (IP, time), and resource states, overriding flat hierarchical RBAC matrices. More details: https://www.aboutiam.com/encyclopedia/?term=abac

Question: What is Active Directory (AD) (Active Directory Domain Services) in Identity Security?
Answer: Analogy: The central registry office of a massive skyscraper corporate headquarters. It tracks every single employee, computer, printer, and elevator security key, allowing administrators to push global rules to all offices in seconds. Technical Specification: Microsoft's proprietary directory service implementing hierarchical object databases containing users, groups, and devices. Operates via Kerberos/NTLM authentication and supports LDAP queries and Group Policy Objects (GPOs). More details: https://www.aboutiam.com/encyclopedia/?term=active_directory

Question: What is Access Token (Access Token (OAuth 2.0 Payload)) in Identity Security?
Answer: Analogy: A Bluetooth hotel keycard. You scan it at your room door, and the lock opens because the bouncer receptionist signed it, even though the door lock doesn't know your name or home address. Technical Specification: RFC 6749. A string or JWT representing authorization granted to the client application. It is passed in HTTP headers (`Authorization: Bearer <token>`) to authenticate requests at resource APIs. More details: https://www.aboutiam.com/encyclopedia/?term=access_token

Question: What is Authentication (AuthN) (Authentication) in Identity Security?
Answer: Analogy: Showing your physical passport to a customs officer. It proves that you are indeed the human person pictured on the document. Technical Specification: The security process of validating the claimed identity of a user, service, or device, typically verified via credentials (passwords, TOTP tokens, or cryptographic signatures). More details: https://www.aboutiam.com/encyclopedia/?term=authn

Question: What is Authorization (AuthZ) (Authorization) in Identity Security?
Answer: Analogy: The travel Visa stamp inside your passport. The border guard reads it to see if you have legal permission to work or only visit, after you already proved who you are. Technical Specification: The process of determining whether an authenticated entity has permission to perform a specific action or access a target resource (e.g. read, write, delete), managed via RBAC, ABAC, or policies. More details: https://www.aboutiam.com/encyclopedia/?term=authz

Question: What is BFF Pattern (Backend-for-Frontend Architectural Pattern) in Identity Security?
Answer: Analogy: Hiring a personal lawyer to do your business. Instead of sending sensitive secrets directly to the front-line browser, your browser talks to a local secure server (BFF) which manages the keys safely behind closed doors. Technical Specification: A secure design pattern for single-page applications. The SPA delegates OAuth token storage and session management to a secure server backend. The backend manages tokens and authenticates the SPA via encrypted, HttpOnly, SameSite cookies. More details: https://www.aboutiam.com/encyclopedia/?term=bff

Question: What is bcrypt (bcrypt Password Hashing Algorithm) in Identity Security?
Answer: Analogy: bcrypt is a lock that is deliberately slow to pick, on purpose — so that even if a thief steals the entire box of locks (your database), trying keys against even one lock is impractically slow. Technical Specification: A Blowfish-based adaptive key-derivation and password hashing function. Features a configurable work factor that doubles the computation time per increment to resist brute-force hardware scaling. More details: https://www.aboutiam.com/encyclopedia/?term=bcrypt

Question: What is CAEP (Continuous Access Evaluation Protocol) in Identity Security?
Answer: Analogy: A security guard constantly walking with you inside the bank. If you suddenly pull out a camera (a context change), they escort you out immediately, rather than waiting for your visitor badge to expire at 5 PM. Technical Specification: An active profile of the Shared Signals Framework (RFC 9396) enabling Identity Providers to push real-time session revocation events (e.g., password resets, location anomalies) directly to Relying Party APIs to terminate active access tokens. More details: https://www.aboutiam.com/encyclopedia/?term=caep

Question: What is CIAM (Customer Identity & Access Management) in Identity Security?
Answer: Analogy: The frictionless signup door of an online store. It makes logging in incredibly easy (e.g. Sign in with Google, fingerprint touch), tracks marketing profiles, and scales to millions of users without crashing. Technical Specification: A specialized branch of identity management optimized for customer-facing systems. Focuses on UX, scalability, social logins, consent management (GDPR), API integrations, and anomaly detection. More details: https://www.aboutiam.com/encyclopedia/?term=ciam

Question: What is DID (Decentralized Identifier) in Identity Security?
Answer: Analogy: An official physical driver's license card. You carry it in your wallet, show it to whom you want, and the DMV (Identity Provider) is never notified when or where you showed it. Technical Specification: A standard W3C URI string resolving to cryptographic public keys held on a tamper-proof blockchain or distributed ledger, allowing users to verify their identities without centralized servers. More details: https://www.aboutiam.com/encyclopedia/?term=did

Question: What is Directory Services (Directory Services & Directories) in Identity Security?
Answer: Analogy: An office telephone directory or organigram, mapping out people under specific departments, floors, and roles. Technical Specification: A specialized hierarchical database optimized for read-heavy operations, organizing corporate resources, users, and credentials under domain trees accessed via LDAP or Active Directory protocols. More details: https://www.aboutiam.com/encyclopedia/?term=directory

Question: What is FIDO2 / WebAuthn (FIDO2 & Web Authentication standard) in Identity Security?
Answer: Analogy: Unlocking your computer with your face. Instead of typing a secret password, your device dynamically signs a cryptographic message locally and proves you possess the device. Technical Specification: The unified passwordless authentication standard combining W3C WebAuthn and CTAP2. Uses asymmetric public-key cryptography to perform secure, phishing-resistant logins natively in-browser. More details: https://www.aboutiam.com/encyclopedia/?term=fido2

Question: What is IdP (Identity Provider) in Identity Security?
Answer: Analogy: The government passport agency. They verify your documents, print your passport, and sign it so that other countries can trust it is authentic. Technical Specification: A central federation authority (e.g. Okta, Keycloak, Entra) that creates, maintains, and manages identity records, performing the actual authentication and issuing security tokens (OIDC/SAML) to client apps. More details: https://www.aboutiam.com/encyclopedia/?term=idp

Question: What is ID Token (ID Token (OpenID Connect Assertion)) in Identity Security?
Answer: Analogy: A laminated corporate name badge. It explicitly states your name, department, photo, and badge expiration date directly on the card so anyone can read it at a glance. Technical Specification: OIDC Core 1.0. A JSON Web Token (JWT) containing cryptographically signed claims verifying the user's identity (such as `sub`, `name`, `email`, `auth_time`). It is intended strictly for the client application. More details: https://www.aboutiam.com/encyclopedia/?term=id_token

Question: What is IGA (Identity Governance and Administration) in Identity Security?
Answer: Analogy: An annual school attendance audit. Managers review student files, confirm who has graduated (reclaiming building cards), and verify who needs specific library access. Technical Specification: A security discipline focused on compliance, auditing, role administration, segregation of duties (SoD), and user access reviews to prevent entitlement accumulation. More details: https://www.aboutiam.com/encyclopedia/?term=iga

Question: What is JWE (JSON Web Encryption) in Identity Security?
Answer: Analogy: Putting a letter inside a steel lockbox. Unlike a postcard (JWS) where anyone can read the text but cannot forge the signature, a JWE ensures only the recipient with the exact key can read the contents. Technical Specification: RFC 7516 standard. A JWE encrypts the payload claims, hiding the data entirely from intermediaries. Typically uses hybrid encryption: symmetric CEK for the payload, wrapped asymmetrically for the recipient. More details: https://www.aboutiam.com/encyclopedia/?term=jwe

Question: What is JWKS (JSON Web Key Set) in Identity Security?
Answer: Analogy: A notary public publishing their official signature seal on a public library bulletin board. Anyone can verify the seal on a document is authentic by comparing it to the public board. Technical Specification: RFC 7517. A JSON structure containing a list of public cryptographic keys issued by an Identity Server, allowing relying applications to dynamically verify JWT signatures via `/.well-known/jwks.json`. More details: https://www.aboutiam.com/encyclopedia/?term=jwks

Question: What is JWS (JSON Web Signature) in Identity Security?
Answer: Analogy: A signed check from a bank. The text on the check is completely visible (not encrypted), but the signed line proves that the check was issued by the bank and has not been altered. Technical Specification: RFC 7515. A standard representing a cryptographically secured JSON structure, binding signature checksums (HMAC or RSA) to the header and payload base64url blocks to prevent tampering. More details: https://www.aboutiam.com/encyclopedia/?term=jws

Question: What is JWT (JSON Web Token) in Identity Security?
Answer: Analogy: A digital, self-contained passport card containing your name, photo, and signature. Any machine can read the card and trust the text because the government signed the signature block. Technical Specification: RFC 7519. A compact, URL-safe string representing claims encoded as a JSON object, composed of three dot-separated blocks: Header, Payload, and Signature (`xxxxx.yyyyy.zzzzz`). More details: https://www.aboutiam.com/encyclopedia/?term=jwt

Question: What is Kerberos (Kerberos Authentication Protocol) in Identity Security?
Answer: Analogy: Like getting into a highly secure cinema: you buy a main entry ticket (Ticket Granting Ticket) once at the box office. Then, you trade it for individual cinema tickets (Service Tickets) at each room door without showing your ID again. Technical Specification: RFC 4120. A symmetric, ticket-based computer network authentication protocol using Key Distribution Centers (KDC) to authenticate clients to server applications securely without sending passwords over the wire. More details: https://www.aboutiam.com/encyclopedia/?term=kerberos

Question: What is LDAP (Lightweight Directory Access Protocol) in Identity Security?
Answer: Analogy: Like looking up a book in a library card catalog using a nested system: Floor -> Aisle -> Shelf -> Subject -> Book. Technical Specification: RFC 4511. An active application protocol used to query and manage hierarchical directory services over IP networks. Utilizes distinguished names (DNs) and nested schemas to retrieve user/group records. More details: https://www.aboutiam.com/encyclopedia/?term=ldap

Question: What is MFA (Multi-Factor Authentication) in Identity Security?
Answer: Analogy: Unlocking a high-security vault: you have to type the code (factor 1: what you know), insert a key card (factor 2: what you have), and scan your fingerprint (factor 3: what you are). Technical Specification: A security mechanism requiring users to present two or more independent authentication factors (Knowledge, Possession, Inherence) to successfully verify identity. More details: https://www.aboutiam.com/encyclopedia/?term=mfa

Question: What is OAuth 2.0 / 2.1 (Open Authorization Framework) in Identity Security?
Answer: Analogy: A hotel electronic card. It is a key that lets you open a specific door for a specific time, without giving you ownership of the building or revealing your personal details. Technical Specification: RFC 6749 & OAuth 2.1. An industry-standard authorization framework allowing third-party applications to obtain limited access to an HTTP resource on behalf of a resource owner via access tokens. More details: https://www.aboutiam.com/encyclopedia/?term=oauth

Question: What is OIDC (OpenID Connect) in Identity Security?
Answer: Analogy: Adding a photo ID card inside your hotel keycard envelope. Not only can you unlock the door, but the hotel room bouncer also immediately knows your name and email. Technical Specification: An identity layer built directly on top of the OAuth 2.0 authorization framework, standardizing user authentication and profile attributes using JSON Web Tokens (`id_token`). More details: https://www.aboutiam.com/encyclopedia/?term=oidc

Question: What is PAM (Privileged Access Management) in Identity Security?
Answer: Analogy: A high-security vault containing master keys for your cloud servers. Only authorized technicians can check out a key, their screen is fully recorded while they use it, and the key automatically self-destructs after 1 hour. Technical Specification: A governance sub-field focused on securing, monitoring, rotating, and recording privileged administrative credentials (SSH keys, root passwords, service keys) under Just-in-Time conditions. More details: https://www.aboutiam.com/encyclopedia/?term=pam

Question: What is Passkeys (Passkeys (Biometric Credentials)) in Identity Security?
Answer: Analogy: Unlocking your house with your fingerprint. The fingerprint never leaves your body, and there is no physical key under the welcome mat for an attacker to steal. Technical Specification: Synced, domain-bound cryptographic credentials utilizing public-key cryptography (WebAuthn). Completely replaces passwords, ensuring immune defenses against phishing attacks. More details: https://www.aboutiam.com/encyclopedia/?term=passkey

Question: What is PKCE (Proof Key for Code Exchange) in Identity Security?
Answer: Analogy: Like leaving a secret half-torn dollar bill at the hotel front desk when checking in. When you return later to get your room key, you must present the exact matching torn half to prove you are the same person. Technical Specification: RFC 7636 standard. Prevents authorization code interception attacks on public clients. The client generates a random `code_verifier`, hashes it to a `code_challenge` for the front-channel, and proves it on the back-channel token exchange. More details: https://www.aboutiam.com/encyclopedia/?term=pkce

Question: What is RBAC (Role-Based Access Control) in Identity Security?
Answer: Analogy: Like assigning keys based on job descriptions: everyone on the finance team gets the keys to the accounting file cabinet, and everyone on engineering gets the keys to the server room. Technical Specification: An authorization framework where access permissions are bound to logical "Roles" (e.g., editor, admin, viewer) and users are assigned to roles, reducing policy management overhead. More details: https://www.aboutiam.com/encyclopedia/?term=rbac

Question: What is ReBAC (Relationship-Based Access Control) in Identity Security?
Answer: Analogy: You can view a family photo album because you are the "child" of the owner, not because your job title says "Photo Viewer". Access is determined by your relationship to the file owner. Technical Specification: An authorization model (Google Zanzibar standard) evaluating access based on a graph of relationships between users and objects (e.g., "User A is owner of Document B; Folder C contains Document B"). More details: https://www.aboutiam.com/encyclopedia/?term=rebac

Question: What is SAML 2.0 (Security Assertion Markup Language) in Identity Security?
Answer: Analogy: A physical passport. The border control (Service Provider) lets you in because they trust the visa stamp (XML Digital Signature) applied by your home government (Identity Provider). Technical Specification: A heavyweight, XML-based open standard for exchanging authentication and authorization data between an IdP and an SP, heavily relying on XML Digital Signatures to prevent assertion tampering. More details: https://www.aboutiam.com/encyclopedia/?term=saml

Question: What is SCIM 2.0 (System for Cross-domain Identity Management) in Identity Security?
Answer: Analogy: An automated megaphone. When HR hires you, the megaphone yells to Slack, AWS, and Salesforce simultaneously to create your accounts using the exact same standard form. Technical Specification: RFC 7643. An open standard providing a common RESTful API schema (JSON) for managing user and group identities across cloud applications, eliminating custom API integration scripts. More details: https://www.aboutiam.com/encyclopedia/?term=scim

Question: What is SSF (Shared Signals Framework) in Identity Security?
Answer: Analogy: If an alarm goes off at one bank, they instantly broadcast alert signals to all neighboring banks so they can lock their doors, too. Technical Specification: An open standardization framework (RFC 9396) enabling disparate SaaS platforms (e.g. Salesforce, Okta, Slack) to subscribe and exchange real-time JSON security event alerts. More details: https://www.aboutiam.com/encyclopedia/?term=ssf

Question: What is SSO (Single Sign-On) in Identity Security?
Answer: Analogy: Buying a secure entry wristband once at an amusement park. You show the wristband at every ride to enter immediately, without showing your wallet or ID at each separate gate. Technical Specification: An authentication mechanism allowing a user to authenticate once to a central authority, gaining access to multiple independent applications without re-prompting credentials. More details: https://www.aboutiam.com/encyclopedia/?term=sso

Question: What is TOTP (Time-Based One-Time Password) in Identity Security?
Answer: Analogy: A bank vault code that changes every 30 seconds. Both you and the bank share a secret clock mechanism that generates the exact same matching code at the exact same second. Technical Specification: RFC 6238. An algorithm generating a one-time password by hashing a shared secret key with the current timestamp, securing secondary user verification factors. More details: https://www.aboutiam.com/encyclopedia/?term=totp

Question: What is Verifiable Credentials (Verifiable Credentials (W3C standard)) in Identity Security?
Answer: Analogy: A digital university diploma inside your mobile wallet. You can show it to a hiring employer, and they can instantly verify it is authentic using the university's public key, without ever contacting the university. Technical Specification: W3C standard. A cryptographically signed digital assertion representing qualification claims, allowing decentralised verification of user credentials without server-to-server redirects. More details: https://www.aboutiam.com/encyclopedia/?term=vc

Question: What is Zero Trust (Zero Trust Security Architecture) in Identity Security?
Answer: Analogy: A maximum-security military lab. Passing the main front gate isn't enough; every single door, terminal, and filing cabinet requires a separate badge scan, device posture check, and authentication, every single time. Technical Specification: NIST SP 800-207. A security framework based on the premise: "Never Trust, Always Verify." Treats all network traffic as hostile, evaluating access decisions dynamically at Policy Decision Points (PDP). More details: https://www.aboutiam.com/encyclopedia/?term=zero_trust

Question: What is OneWelcome (Thales OneWelcome Identity Platform) in Identity Security?

It seamlessly guides guest registrations, manages GDPR room privacy preferences, and delegates keycard distributions to travel agency partners. Technical Specification: A leading European Customer and Partner IAM (CIAM & B2B) platform specializing in no-code visual workflow orchestration, user consent management, and partner-delegated administration. Technical Specification: Thales' military-grade access management service delivering adaptive MFA and context-aware Single Sign-On (SSO), using physical HSMs to protect all cryptographic signing keys. Question: What is Identity Orchestration (Identity Orchestration & Externalized Authorization) in Identity Security?

Question: What is DPoP (Demonstrating Proof-of-Possession (RFC 9449)) in Identity Security?
Answer: Analogy: Like wrapping your bearer keycard in a fingerprint-locked sleeve. Even if a pickpocket steals the card, they cannot use it because it will only unlock if presented alongside your active biometric thumbprint (the client's private key signature). Technical Specification: RFC 9449. A security extension for OAuth 2.0 Access and Refresh tokens. Requires the client to generate a local asymmetric key pair and sign a JWS containing the target HTTP request parameters (method, URI, timestamp). This binds the token to that specific client, preventing token replay attacks if intercepted. More details: https://www.aboutiam.com/encyclopedia/?term=dpop

Question: What is FAPI (Financial-grade API Security Profile) in Identity Security?
Answer: Analogy: An armored bank transport truck instead of a standard courier envelope. Every single lock, hinge, and dispatch time is cryptographically audited and verified to prevent high-value bank robberies. Technical Specification: An OpenID Foundation security profile. Establishes a highly hardened layer on top of OAuth 2.0 and OIDC. Mandates mutual TLS (mTLS), strict asymmetric public key authentication, cryptographic request object signings (PAR), and sender-constrained DPoP tokens to secure financial Open Banking APIs. More details: https://www.aboutiam.com/encyclopedia/?term=fapi

Question: What is GNAP (Grant Negotiation and Authorization Protocol) in Identity Security?
Answer: Analogy: Like a digital lawyer drawing up a bespoke contract. Instead of just showing a generic badge (a token), the client and server negotiate exact, custom access boundaries and parameters on the spot before any key is issued. Technical Specification: A prospective successor framework to OAuth 2.0 (RFC 6749). Decouples client authentication, user consent, and token issuance into a highly expressive, single negotiation request-response protocol, eliminating the need for complex browser redirects and implicit flow hacks. More details: https://www.aboutiam.com/encyclopedia/?term=gnap

Question: What is SCIM PATCH (SCIM 2.0 Attribute-Level Reconciliation) in Identity Security?
Answer: Analogy: Making a minor edit on page 4 of a document instead of completely discarding the book, rewriting everything, and printing a new copy from scratch. Technical Specification: RFC 7644. A REST API method enabling partial, attribute-level modifications inside SCIM 2.0 directories. Supports "add", "remove", and "replace" operations, dramatically reducing network payload overhead and preventing race-conditions. More details: https://www.aboutiam.com/encyclopedia/?term=scim_patch

Question: What is mTLS (Mutual Transport Layer Security) in Identity Security?
Answer: Analogy: A bank teller verifying your ID, while you simultaneously demand to see the teller's official badge. Both parties must prove who they are before any money is slid through the slot. Technical Specification: Mutual Transport Layer Security. An extension of TLS where both the client and server validate each other's X.509 digital certificates before establishing an encrypted tunnel, forming the core perimeter control for zero-trust microservices. More details: https://www.aboutiam.com/encyclopedia/?term=mtls

Question: What is PAR (Pushed Authorization Requests (RFC 9126)) in Identity Security?
Answer: Analogy: Handing your confidential medical records directly to the doctor behind closed doors, and getting a tiny claims ticket to show the receptionist, instead of walking through the crowded lobby waving your records in the air. Technical Specification: RFC 9126. An OAuth 2.0 security extension. The client "pushes" sensitive authorization parameters (like scopes and request URIs) directly to the IdP backchannel over HTTPS, receiving a short-lived "request_uri" ticket. The client browser redirect is then executed strictly with this ticket, preventing parameter tampering. More details: https://www.aboutiam.com/encyclopedia/?term=par

Question: What is DMARC (Domain-based Message Authentication, Reporting, and Conformance) in Identity Security?
Answer: Analogy: A corporate mailroom stamping every outgoing envelope with a wax seal, and telling all post offices to shred any envelope claiming to be from them that lacks the seal. Technical Specification: RFC 7489. An email authentication protocol that builds upon SPF and DKIM. Enables domain owners to publish strict DNS policy records specifying how receiving mail servers should handle unauthorized spoofs (e.g. p=reject), protecting identity domains from phishing. More details: https://www.aboutiam.com/encyclopedia/?term=dmarc

Question: What is ZKP (Zero-Knowledge Proof (Decentralized Identity)) in Identity Security?
Answer: Analogy: Proving to a bartender you are over 21 by showing a glowing green light on your phone, without revealing your actual driver's license, name, or birthdate. Technical Specification: A cryptographic method by which one party (the prover) can prove to another party (the verifier) that a given statement is true, without conveying any information beyond the statement's validity (e.g. proof of credential ownership or mathematical bounds). More details: https://www.aboutiam.com/encyclopedia/?term=zkp

Question: What is KMS (Key Management Service & Hardware HSMs) in Identity Security?
Answer: Analogy: A locked room inside a secure bank vault where keys are generated, stored, and used to sign/decrypt documents. The keys never leave the locked room, and any signing request is executed inside under strict surveillance. Technical Specification: A cloud or hardware-backed (HSM) system offering centralized key generation, lifecycle management, rotation, and cryptographic operations, securing Master Keys and DEKs. More details: https://www.aboutiam.com/encyclopedia/?term=kms

Question: What is ABAC Policy Engine (Dynamic Attribute-Based Evaluation Gateway) in Identity Security?

Technical Specification: A Policy Decision Point (PDP) evaluating incoming access requests against Attribute-Based rules, utilizing context (time, location), user attributes (clearance, roles), and resource metadata dynamically. Question: What is CIBA (Client-Initiated Backchannel Authentication) in Identity Security?

The approval happens on a separate device (your phone) while you keep sitting at a completely different one (a smart TV or kiosk). Technical Specification: An OpenID Foundation extension to OIDC enabling decoupled authentication: a consumption device (smart TV, kiosk, call center agent) initiates a login request via the backchannel, and the actual user approval happens asynchronously on a separate authentication device (e.g. a mobile app push). Question: What is RAR (Rich Authorization Requests (RFC 9396)) in Identity Security?

Extends OAuth 2.0 beyond flat string `scope` values by letting clients request fine-grained, structured JSON authorization details (exact amounts, resource identifiers, actions), commonly used in Open Banking and FAPI-profile deployments. More details: https://www.aboutiam.com/encyclopedia/?term=rar

Question: What is SD-JWT (Selective Disclosure JSON Web Token) in Identity Security?
Answer: Analogy: Handing someone a diploma where individual lines (your major, your GPA, your graduation date) are each covered by a removable sticker. You peel off only the stickers relevant to the person asking, without invalidating the university's original seal. Technical Specification: An IETF format layering selective disclosure over JWTs: the issuer hashes and commits individual claims as separate disclosable blocks, letting a holder reveal only a subset of claims to a verifier while the original issuer signature still validates the presented subset. More details: https://www.aboutiam.com/encyclopedia/?term=sd_jwt

Question: What is mDL / mDoc (Mobile Driver's License (ISO/IEC 18013-5)) in Identity Security?
Answer: Analogy: Tapping your phone at airport security instead of handing over a plastic driver's license. More details: https://www.aboutiam.com/encyclopedia/?term=mdl

Question: What is RADIUS (Remote Authentication Dial-In User Service) in Identity Security?

A legacy but still widely deployed AAA protocol used by network devices (VPN concentrators, Wi-Fi access points, switches) to centralize authentication, authorization, and accounting against a shared server, typically backed by Active Directory or LDAP. Question: What is OCSP (Online Certificate Status Protocol) in Identity Security?

Technical Specification: RFC 6960. A real-time protocol allowing a relying party to query a Certificate Authority (or its designated responder) about the current revocation status of a single X.509 certificate, avoiding the need to download a full Certificate Revocation List. Question: What is CRL (Certificate Revocation List) in Identity Security?

Technical Specification: RFC 5280. A digitally signed, timestamped list published periodically by a Certificate Authority enumerating serial numbers of X.509 certificates that have been revoked before their natural expiry, checked by clients as an alternative or fallback to OCSP. Technical Specification: A JSON-LD document resolvable from a DID, containing the public keys, authentication methods, and service endpoints associated with that decentralized identifier, enabling verifiers to cryptographically validate signatures made by the DID's controller. Question: What is OID4VC (OpenID for Verifiable Credentials) in Identity Security?
Answer: Analogy: Bolting the familiar OAuth/OIDC login plumbing onto a digital wallet, so issuing and presenting a verifiable diploma or ID card feels just like a normal "Sign in with…" flow developers already know. Technical Specification: A family of OpenID Foundation specifications (OID4VCI for issuance, OID4VP for presentation) that extend OAuth 2.0/OIDC flows to issue and present W3C Verifiable Credentials, bridging decentralized identity into familiar OAuth infrastructure. More details: https://www.aboutiam.com/encyclopedia/?term=oid4vc

Question: What is SIOP (Self-Issued OpenID Provider) in Identity Security?
Answer: Analogy: A user acting as their own passport office — issuing themselves a signed ID token straight from their personal wallet instead of asking a company-run identity provider to do it. Technical Specification: An OIDC extension allowing an end-user's wallet or local agent to act as its own OpenID Provider, self-issuing an ID Token containing DID-based claims, enabling relying parties to authenticate a user directly from their decentralized identity without a hosted IdP. More details: https://www.aboutiam.com/encyclopedia/?term=siop

Question: What is eIDAS (Electronic Identification, Authentication and Trust Services Regulation) in Identity Security?
Answer: Analogy: An EU-wide agreement that a digital ID card issued in one member country must be honored just as readily by government services in every other member country. Technical Specification: An EU regulation establishing a legal framework for cross-border electronic identification and trust services (e-signatures, e-seals), with eIDAS 2.0 mandating an EU Digital Identity Wallet supporting W3C Verifiable Credentials for citizens across member states. More details: https://www.aboutiam.com/encyclopedia/?term=eidas

Question: What is Levels of Assurance (IAL/AAL/FAL) (NIST 800-63 Identity, Authenticator & Federation Assurance Levels) in Identity Security?
Answer: Analogy: Grading how strongly you trust a claimed identity like a hotel grading star ratings: a 1-star check just glances at a name typed on a form, while a 3-star check involves notarized documents, a live photo match, and a background check. Technical Specification: NIST SP 800-63-3 defines three independent assurance dimensions: IAL (confidence in identity proofing), AAL (strength of the authentication mechanism), and FAL (strength of a federation assertion), each rated 1-3, used by government and regulated systems to specify required rigor. More details: https://www.aboutiam.com/encyclopedia/?term=assurance_levels

Question: What is Just-In-Time (JIT) Access (Just-In-Time Privileged Access) in Identity Security?
Answer: Analogy: A maintenance worker who requests a temporary elevator override key for exactly the 20 minutes he needs it, rather than carrying a permanent override key on his belt all year. Technical Specification: A PAM control that grants elevated entitlements for a narrow, time-boxed window tied to an approved request or workflow, automatically expiring the grant afterward, sharply reducing the standing-privilege attack surface compared to permanent admin rights. More details: https://www.aboutiam.com/encyclopedia/?term=jit_access

Question: What is De-provisioning (Account De-provisioning) in Identity Security?
Answer: Analogy: Cutting up an employee's building badge and changing the office locks the moment their last day ends. Technical Specification: The automated (typically SCIM-driven) process of disabling or deleting a user's accounts and entitlements across every connected system the instant their employment or contract ends, closing the window attackers exploit via orphaned accounts. More details: https://www.aboutiam.com/encyclopedia/?term=deprovisioning

Question: What is Birthright Access (Birthright Access) in Identity Security?
Answer: Analogy: Every new employee automatically getting a building badge, an email account, and a parking pass on day one, without anyone having to individually request each one. Technical Specification: A baseline set of entitlements (email, VPN, intranet, core SaaS) automatically granted to every identity in a given role or department upon onboarding, driven by HR-triggered provisioning rules rather than individual access requests. More details: https://www.aboutiam.com/encyclopedia/?term=birthright_access

Question: What is Identity Lifecycle Management (Identity Lifecycle Management (Joiner-Mover-Leaver)) in Identity Security?
Answer: Analogy: HR's full playbook for an employee's entire journey — issuing their first badge on day one, reprogramming it when they change floors, and confiscating it the day they leave. Technical Specification: The end-to-end governance of an identity's entitlements across the Joiner-Mover-Leaver (JML) lifecycle: provisioning birthright access at hire, adjusting entitlements on role change, and fully de-provisioning at termination, typically orchestrated by an IGA platform integrated with HR systems. More details: https://www.aboutiam.com/encyclopedia/?term=identity_lifecycle_management

Question: What is KBA (Knowledge-Based Authentication) in Identity Security?
Answer: Analogy: A bank teller verifying your identity by asking "what street did you grow up on?" — questions only the real you (or someone who's done their research) would know the answer to. Technical Specification: An identity-verification method relying on shared secrets or personal history questions (mother's maiden name, previous addresses), increasingly deprecated in favor of stronger methods since answers are often discoverable via social engineering or data breaches. More details: https://www.aboutiam.com/encyclopedia/?term=kba

Question: What is Account Recovery (Account Recovery & Backup Authentication) in Identity Security?
Answer: Analogy: The spare house key hidden with a trusted neighbor, used only when you've locked yourself out and lost your primary key entirely. Technical Specification: The set of fallback mechanisms (backup codes, recovery email/phone, trusted contacts, identity re-proofing) that let a legitimate user regain access after losing their primary authenticator, while being hardened enough that attackers cannot abuse the same path to hijack the account. More details: https://www.aboutiam.com/encyclopedia/?term=account_recovery

Question: What is Identity Proofing (Identity Proofing) in Identity Security?
Answer: Analogy: The passport office actually examining your birth certificate and utility bills before issuing you a passport, rather than just taking your word for who you are. Technical Specification: The process of collecting and validating evidence (government ID scans, biometric liveness checks, address verification) to establish that a claimed identity genuinely corresponds to a real person, forming the basis of a system's NIST 800-63 Identity Assurance Level. More details: https://www.aboutiam.com/encyclopedia/?term=identity_proofing

Question: What is KYC (Know Your Customer) in Identity Security?
Answer: Analogy: A bank legally required to check your government ID and address before letting you open an account, so criminals can't open accounts under fake names. Technical Specification: A regulatory requirement (particularly in financial services) mandating identity verification and risk assessment of customers before onboarding, typically implemented via document verification, sanctions-list screening, and biometric liveness detection. More details: https://www.aboutiam.com/encyclopedia/?term=kyc

Question: What is Social Login (Social Login / Social Identity Federation) in Identity Security?
Answer: Analogy: Using your existing driver's license to check into a hotel instead of filling out a brand-new hotel-specific ID form every single time you travel. Technical Specification: A CIAM pattern where an application delegates authentication to a large consumer identity provider (Google, Apple, Facebook) via OIDC/OAuth, reducing signup friction at the cost of dependency on the third-party provider's availability and data-sharing policies. More details: https://www.aboutiam.com/encyclopedia/?term=social_login

Question: What is Magic Link (Magic Link Authentication) in Identity Security?
Answer: Analogy: A one-time paper ticket mailed straight to your home address — clicking it is proof enough that you control that mailbox, so no password is ever needed. Technical Specification: A passwordless login method that emails or texts a single-use, time-limited authentication URL to a pre-verified address; clicking it proves possession of that inbox/phone and establishes a session without a shared-secret password. Question: What is Account Lockout (Account Lockout Policy) in Identity Security?
Answer: Analogy: A padlock that jams itself shut for 15 minutes after five wrong combination attempts in a row, buying time before anyone can try a sixth guess. Technical Specification: A defensive control that temporarily or permanently disables an account after a configured number of consecutive failed authentication attempts, mitigating brute-force and credential-stuffing attacks at the cost of potential denial-of-service against legitimate users if not rate-tuned carefully. Question: What is SSPR (Self-Service Password Reset) in Identity Security?
Answer: Analogy: A hotel kiosk that lets a guest who forgot their room number reprint their own keycard after verifying a few personal details, without ever needing to wake up the night manager. Technical Specification: A capability allowing users to reset a forgotten password themselves after passing an identity-verification challenge (MFA, security questions, email/SMS verification), reducing helpdesk password-reset ticket volume, one of the highest-cost categories of IT support tickets. ## Section 2: Identity Standards & Protocols Q&A

Question: What is the OAuth 2.1 protocol and what security challenges does it resolve?
Answer: Full Name: Consolidated Authorization Framework. Problem Resolved: OAuth 2.0 had multiple legacy grant types (Implicit, Password) that exposed security credentials in browser histories and redirect flows, leading to token thefts.. Why it exists: To establish a secure-by-default baseline for modern API and application authorization without legacy security loopholes. Key Best Practices: Mandate PKCE S256 verifications on all public clients., Validate redirects against exact string comparisons, disabling wildcard matching., Enforce Sender-Constrained tokens (DPoP) on high-risk APIs. Full spec: https://www.aboutiam.com/standards/?standard=oauth21

Question: What is the OIDC 1.0 protocol and what security challenges does it resolve?
Answer: Full Name: OpenID Connect Core 1.0. Problem Resolved: OAuth 2.0 was designed for authorization (delegated access), leaving developers to hand-roll custom user authentication structures, leading to non-standard, vulnerable "Login with OAuth" implementations.. Why it exists: To standardize user authentication, introducing a cryptographically signed ID Token (JWT) and a standard /userinfo endpoint. Key Best Practices: Always validate JWT signatures on downstream resource gates., Cache and rate-limit JWKS endpoint fetches strictly., Reject "none" algorithms explicitly in signature verification libraries. Full spec: https://www.aboutiam.com/standards/?standard=oidc

Question: What is the SCIM 2.0 protocol and what security challenges does it resolve?
Answer: Full Name: System for Cross-domain Identity Management. Problem Resolved: Manual user onboarding, offboarding, and directory synchronization across hundreds of separate corporate SaaS apps led to high operational overhead and orphaned accounts.. Why it exists: To define a standardized, REST/JSON-based resource schema for Users and Groups, enabling automated Identity Lifecycle synchronization. Key Best Practices: Secure SCIM API endpoints strictly using OAuth 2.0 Bearer tokens or mTLS certificates., Sanitize and validate filter parameter parameters strictly before querying databases., Validate incoming SCIM payloads against strict, defined schema blueprints. Full spec: https://www.aboutiam.com/standards/?standard=scim20

Question: What is the WebAuthn protocol and what security challenges does it resolve?
Answer: Full Name: W3C Web Authentication (FIDO2). Problem Resolved: Passwords are vulnerable to phishing, databases leaks, or local keylogging, while legacy SMS-based MFA remains vulnerable to high-tech SIM swapping.. Why it exists: To establish a global, passwordless authentication profile using hardware-secured asymmetric keypairs where servers only store the client public key. Key Best Practices: Validate incoming origin domains strictly inside clientDataJSON to prevent phishing., Enforce User Verification (UV = biometrics/PIN) on sensitive transaction routes., Assert credentials are bound strictly to hardware enclaves (RP ID matching). Full spec: https://www.aboutiam.com/standards/?standard=webauthn

Question: What is the FIDO Certification Programs protocol and what security challenges does it resolve?
Answer: Full Name: FIDO Alliance Authenticator & Biometric Certification. Problem Resolved: "FIDO2 compliant" is a marketing claim any vendor can make; without independent testing, a buyer has no way to verify a device correctly implements attestation, key storage isolation, or presentation-attack detection the way the spec assumes.. Why it exists: To give relying parties and buyers a real, third-party-tested guarantee behind the "FIDO Certified" label, at graduated assurance levels rather than one pass/fail bar — a hardware security key and a phone's platform authenticator warrant different scrutiny. Key Best Practices: When specifying a hardware key requirement, name the actual certification level needed (e.g. "FIDO2 L2 or higher"), not just "FIDO2 certified.", For biometric unlock flows, check for PAD Level 2 or 3 certification specifically — Authenticator Certification alone says nothing about spoof resistance., Re-verify a product's current certification status against FIDO Alliance's own live directory before procurement — do not rely on a vendor datasheet or a cached snapshot., Last verified: 2026-07-31. For the live, current product directory, see the FIDO Alliance's own certified product site → https://fidoalliance.org/certification/fido-certified-products/ Full spec: https://www.aboutiam.com/standards/?standard=fido-certification

Question: What is the SAML 2.0 protocol and what security challenges does it resolve?
Answer: Full Name: Security Assertion Markup Language 2.0. Problem Resolved: Before SAML, every enterprise app maintained its own username/password store, forcing employees to juggle dozens of separate logins and IT to manage duplicate credential lifecycles.. Why it exists: To let a single, centrally-managed Identity Provider vouch for a user's identity to any number of separate Service Providers via a signed XML "passport" (the Assertion), without the SP ever seeing the user's password. Key Best Practices: Validate the signature against the exact Assertion ID being processed, never trust the first matching node in the XML tree., Enforce assertion Conditions (NotBefore/NotOnOrAfter) and Audience restriction checks strictly., Rotate and hardware-vault (HSM) IdP signing keys; monitor for anomalous signing key export events. Full spec: https://www.aboutiam.com/standards/?standard=saml2

Question: What is the LDAP v3 protocol and what security challenges does it resolve?
Answer: Full Name: Lightweight Directory Access Protocol v3. Problem Resolved: Early X.500 directory access protocols were heavyweight (full OSI stack) and impractical for everyday application use, making simple "find this user's group memberships" queries expensive to implement.. Why it exists: To provide a lean, TCP/IP-native protocol for reading and searching directory entries (users, groups, org units) using a simple string filter syntax. Key Best Practices: Escape all RFC 4515 special filter characters ( \28 \29 \2a \5c \00 ) before interpolating user input., Disable anonymous bind and enforce LDAPS (port 636) or StartTLS for every connection., Apply least-privilege service accounts for read-only directory queries instead of Domain Admin binds. Full spec: https://www.aboutiam.com/standards/?standard=ldapv3

Question: What is the Kerberos protocol and what security challenges does it resolve?
Answer: Full Name: Kerberos Network Authentication Service v5. Problem Resolved: Sending passwords (even hashed) over a shared corporate network for every single service login created a huge sniffing/replay attack surface for internal Windows/Unix networks.. Why it exists: To let a user authenticate once to a trusted KDC and receive short-lived, cryptographically-sealed tickets that can be presented to any number of services without ever re-sending a password. Key Best Practices: Rotate the krbtgt account password twice, on a schedule, especially after any suspected domain compromise., Enforce long, random passwords (or gMSA-managed passwords) for all service accounts to defeat offline Kerberoasting., Monitor for anomalous TGT lifetimes and abnormal ticket-encryption-type downgrades (RC4 vs AES). Full spec: https://www.aboutiam.com/standards/?standard=kerberos

Question: What is the TOTP / HOTP protocol and what security challenges does it resolve?
Answer: Full Name: Time-based & HMAC-based One-Time Password Algorithms. Problem Resolved: Static passwords alone are trivially phished or reused; early hardware OTP tokens (RSA SecurID) were proprietary and expensive, with no open standard for interoperable code generation.. Why it exists: To standardize a simple, open, license-free algorithm for one-time codes so any authenticator app or hardware token can interoperate with any server. Key Best Practices: Generate secrets with a cryptographically secure RNG at a minimum of 160 bits (20 bytes)., Rate-limit and lock out after a small number of failed OTP attempts to blunt brute-force., Prefer phishing-resistant WebAuthn/Passkeys over TOTP for high-value accounts where possible. Full spec: https://www.aboutiam.com/standards/?standard=totp-hotp

Question: What is the RADIUS protocol and what security challenges does it resolve?
Answer: Full Name: Remote Authentication Dial-In User Service. Problem Resolved: Every network access server (VPN concentrator, Wi-Fi controller, switch) needed its own local user database, making centralized policy and consistent MFA enforcement across network edges impossible.. Why it exists: To let any network access device forward an authentication request to a single, centrally managed AAA server, enabling one policy engine for every AAA decision on the network. Key Best Practices: Prefer EAP-TLS (certificate-based) over password-based EAP methods for 802.1X network authentication., Deploy RadSec (RADIUS over TLS/RFC 6614) to encrypt AAA traffic between NAS and server., Use unique, high-entropy shared secrets per NAS device and rotate them on a schedule. Full spec: https://www.aboutiam.com/standards/?standard=radius

Question: What is the JOSE / JWT protocol and what security challenges does it resolve?
Answer: Full Name: JSON Object Signing and Encryption (JWS, JWE, JWK, JWT). Problem Resolved: Before JOSE, every framework invented its own bespoke signed-token format, making cross-platform, interoperable token verification (mobile app ↔ Java backend ↔ Node microservice) a constant integration headache.. Why it exists: To give the industry one compact, base64url-encoded, self-describing structure for signed/encrypted claims that any language's crypto library can produce and verify identically. Key Best Practices: Hard-pin the expected signing algorithm on the verifier side; never trust the "alg" header from the token itself., Prefer short-lived access tokens (minutes) paired with a separately revocable refresh token., Only use JWE algorithms with authenticated encryption (e.g. A256GCM), never unauthenticated CBC modes alone. Full spec: https://www.aboutiam.com/standards/?standard=jose

Question: What is the X.509 PKI & mTLS protocol and what security challenges does it resolve?
Answer: Full Name: X.509 Public Key Infrastructure & Mutual TLS. Problem Resolved: Bearer tokens and passwords can be copied and replayed from any machine; server-only TLS proves the server's identity but leaves the client anonymous at the transport layer, an unacceptable gap for high-assurance service-to-service or workload communication.. Why it exists: To give every party in a connection (not just the server) a verifiable, CA-issued cryptographic identity, and a standard chain-of-trust model (Root → Intermediate → Leaf) for validating it. Key Best Practices: Enforce OCSP stapling or short-lived certificates instead of relying solely on client-side CRL fetches., Store private keys in an HSM, TPM, or cloud KMS rather than as plaintext files on disk., Automate certificate issuance/rotation (e.g. ACME, SPIFFE/SPIRE) to keep lifetimes short and reduce manual renewal risk. Full spec: https://www.aboutiam.com/standards/?standard=x509-pki

Question: What is the RFC 8693 protocol and what security challenges does it resolve?
Answer: Full Name: OAuth 2.0 Token Exchange. Problem Resolved: Microservice chains (Gateway → Service A → Service B) had no standard way to safely narrow a caller's token scope, swap token formats between legacy and modern systems, or attribute a downstream call to both the original user and the calling service.. Why it exists: To standardize how a client presents an existing token to an STS and receives back a new, appropriately-scoped token — carrying delegation ("acting on behalf of") or impersonation semantics explicitly. Key Best Practices: Always include and strictly validate the "aud" claim so an exchanged token only works against its intended service., Preserve the original subject and actor ("act_as") claims through every hop for a full audit trail., Enforce monotonic scope narrowing — an exchanged token must never carry more privilege than its subject token. Full spec: https://www.aboutiam.com/standards/?standard=rfc8693

Question: What is the NIST SP 800-63 protocol and what security challenges does it resolve?
Answer: Full Name: NIST Digital Identity Guidelines. Problem Resolved: Agencies and enterprises had no common vocabulary for "how sure are we this person is who they claim to be" versus "how sure are we this login session is legitimate," leading to inconsistent, all-or-nothing identity assurance decisions.. Why it exists: To let a relying party independently dial in the right level of identity proofing rigor and authentication strength for a given risk profile, rather than treating all logins as equally trustworthy. Key Best Practices: Map each business transaction to an explicit required IAL/AAL/FAL combination before choosing an identity provider., Prefer phishing-resistant authenticators (WebAuthn/Passkeys) to satisfy AAL2/AAL3 rather than OTP-based factors., Use FAL3 (key-bound assertions) for any federation flow protecting highly sensitive resources. Full spec: https://www.aboutiam.com/standards/?standard=nist80063

Question: What is the XACML 3.0 protocol and what security challenges does it resolve?
Answer: Full Name: eXtensible Access Control Markup Language 3.0. Problem Resolved: Access control logic hardcoded into each application (if user.role == "admin") could not be centrally audited, updated, or reused, and offered no standard way to combine multiple overlapping policies consistently.. Why it exists: To externalize authorization decisions into a shared Policy Decision Point (PDP), with a standard request/response schema and explicit rules for combining multiple applicable policies (deny-overrides, permit-overrides, etc.). Key Best Practices: Default to a deny-overrides combining algorithm for any security-sensitive policy set., Fail closed — treat Indeterminate/NotApplicable PDP responses as Deny in the PEP, never as an implicit Permit., Version and test policies with representative request fixtures before deploying combining-algorithm changes. Full spec: https://www.aboutiam.com/standards/?standard=xacml3

Question: What is the GNAP protocol and what security challenges does it resolve?
Answer: Full Name: Grant Negotiation and Authorization Protocol. Problem Resolved: OAuth 2.0's client model assumes a browser-redirect-capable client and bearer tokens; it struggles to natively express non-redirect interaction (CLI tools, IoT devices), multi-party authorization, or sender-constrained tokens without extension RFCs bolted on afterward.. Why it exists: To unify what OAuth had spread across many separate extension RFCs (PKCE, DPoP, device flow, PAR, rich authorization requests) into a single, coherent core protocol designed with those needs in mind from day one. Key Best Practices: Always bind access tokens and continuation tokens to the requesting client's key (httpsig/DPoP-style proof), never bearer-only., Validate the "interact_ref" returned at interaction-finish strictly against the originating grant request state., Model multi-party approval requirements explicitly and verify all required approvals before token issuance. Full spec: https://www.aboutiam.com/standards/?standard=gnap

Question: What is the CAEP / SSF protocol and what security challenges does it resolve?
Answer: Full Name: Continuous Access Evaluation Protocol & Shared Signals Framework. Problem Resolved: OAuth/OIDC sessions are traditionally only re-evaluated when a token expires; a session revoked, or a user's risk score spiking, at the IdP had no standard way to immediately propagate that change to every app currently trusting an old, still-technically-valid token.. Why it exists: To let identity providers proactively push "this session/token should no longer be trusted" (or trust-increasing) signals in real time, closing the gap between an IdP-side risk event and enforcement everywhere that session is used. Key Best Practices: Always verify the SET's JWS signature against the transmitter's published JWKS before acting on any event., Track jti (SET id) to detect and reject replayed events., Pair CAEP with a short-lived polling fallback so a missed push signal is caught on the next natural token refresh. Full spec: https://www.aboutiam.com/standards/?standard=caep-ssf

Question: What is the Verifiable Credentials & DIDs protocol and what security challenges does it resolve?
Answer: Full Name: W3C Verifiable Credentials Data Model & Decentralized Identifiers. Problem Resolved: Traditional federated identity (SAML/OIDC) always requires the Verifier to call back to the original Identity Provider online at login time, giving that IdP visibility into every place the user logs in and creating a single point of failure.. Why it exists: To let a Holder collect signed credentials once and present cryptographic proof of them later, offline, to any Verifier — without the original Issuer being involved in, or even aware of, each individual presentation. Key Best Practices: Use a status list or revocation registry and check it on every presentation, not just at issuance time., Rotate Holder DIDs (or use pairwise DIDs per relationship) to minimize cross-Verifier correlation., Verify the full chain — Issuer DID resolution, signature validity, and expiration — offline before trusting any claim. Full spec: https://www.aboutiam.com/standards/?standard=vc-did

Question: What is the OpenID4VC (OID4VCI / OID4VP) protocol and what security challenges does it resolve?
Answer: Full Name: OpenID for Verifiable Credential Issuance & Presentation. Problem Resolved: The W3C Verifiable Credentials Data Model defines what a credential looks like, but not how a Wallet actually requests one from an Issuer, or presents one to a Verifier, over HTTP — every vendor filled that gap differently until OpenID4VC standardized it on top of OAuth 2.0.. Why it exists: eIDAS 2.0 mandates that every EU member state ship an EUDI (European Digital Identity) Wallet by 2026, and the EU's own Architecture Reference Framework (ARF) selected OpenID4VCI/VP + SD-JWT VC as the interoperable issuance/presentation profile every member state's wallet must speak. Key Best Practices: Only disclose exactly what a Verifier's presentation definition requests — never the full credential — even when the Wallet technically holds more., Bind presentations to the holder's key (Key Binding JWT / cnf claim) so a stolen presentation can't be replayed by someone else., Issue fine-grained, independently disclosable claims (e.g. a standalone `age_over_21` boolean) rather than forcing Wallets to reveal a raw birthdate just to prove an age threshold. Full spec: https://www.aboutiam.com/standards/?standard=openid4vc

Question: What is the SPIFFE / SPIRE protocol and what security challenges does it resolve?
Answer: Full Name: Secure Production Identity Framework For Everyone. Problem Resolved: Microservices traditionally authenticated to each other with long-lived, static API keys or shared certificates baked into config files or environment variables — a huge blast radius if any single service or CI pipeline leaked one.. Why it exists: To give every workload (container, VM, function) a cryptographically verifiable identity that is automatically issued based on runtime attestation (not a static secret), rotated frequently, and portable across clouds and clusters. Key Best Practices: Scope node and workload attestors as tightly as possible (e.g. Kubernetes namespace + service account, not just "any pod on this node")., Keep SVID TTLs short (minutes, not days) so a leaked credential has minimal usable lifetime., Protect the SPIRE Server's signing key in an HSM/KMS and monitor for anomalous registration entry changes. Full spec: https://www.aboutiam.com/standards/?standard=spiffe-spire

Question: What is the DPoP protocol and what security challenges does it resolve?
Answer: Full Name: Demonstrating Proof-of-Possession at the Application Layer. Problem Resolved: Classic OAuth Bearer tokens are usable by anyone who possesses them — if a token leaks (via XSS, a misconfigured log, or a malicious proxy), the thief can replay it from anywhere with zero additional proof required.. Why it exists: To let public clients (SPAs, mobile apps) that can't practically hold an mTLS client certificate still get sender-constrained tokens, using a lightweight, per-request signed JWT proof generated from a client-held key pair. Key Best Practices: Track recently-seen jti values per key and reject duplicates within the proof's validity window., Generate the DPoP key pair in a non-extractable form (e.g. Web Crypto CryptoKey with extractable:false) wherever the runtime supports it., Bind the "htm"/"htu" claims strictly to the exact request method and URL to prevent proof reuse across endpoints. Full spec: https://www.aboutiam.com/standards/?standard=dpop

Question: What is the FAPI 2.0 protocol and what security challenges does it resolve?
Answer: Full Name: Financial-grade API Security Profile 2.0. Problem Resolved: Plain OAuth 2.0 is intentionally flexible so it fits everything from a consumer social-login button to a bank transfer API — but that flexibility means nothing stops an implementer from making choices (bearer tokens, unsigned redirects, parameters in the URL) that are fine for a "log in with Google" button but genuinely dangerous for moving real money.. Why it exists: Open Banking and Open Finance regulations (UK Open Banking, Australia's CDR, Brazil's Open Finance) needed one interoperable, opinionated security profile that every bank and TPP (Third-Party Provider) could implement identically, rather than each regulator inventing its own OAuth hardening rules. Key Best Practices: Require PAR unconditionally — never leave the legacy direct-parameter authorization endpoint enabled alongside it., Bind every issued access and refresh token to the client's mTLS certificate or a DPoP key; reject any token presented without a matching proof., Sign authorization responses (JARM) so the client can cryptographically verify nothing was altered in transit, independent of TLS. Full spec: https://www.aboutiam.com/standards/?standard=fapi2

## Section 3: Incident Response & Mitigation Playbooks Q&A

Question: How do security teams respond to and mitigate a MFA Fatigue Push-Bombing Handovers attack?
Answer: Mapped Category: MFA & Push Fatigue. Attack Vector: MFA Push Notification Exhaustion Hacking. Detailed Playbook Mitigation Steps: Disable standard basic "Approve/Deny" push notification setups globally. -> Enable Context-Aware Number Matching, forcing the user to type digits shown on the login screen. -> Enable location-aware push notification displays, showing the login request IP and location map on the device. -> Enforce alert thresholds to block or lock accounts when more than 5 MFA notifications trigger in 1 minute. Incident console: https://www.aboutiam.com/bulletins/?bulletin=mfa_fatigue

Question: How do security teams respond to and mitigate a Snowflake Customer Tenant Credential Stuffing (UNC5537) attack?
Answer: Mapped Category: Credential & Session Theft. Attack Vector: Credential Stuffing Against MFA-less Customer Accounts. Detailed Playbook Mitigation Steps: Mandate MFA enforcement on every customer/tenant account accessing the SaaS platform, not just administrative logins. -> Enable network policy allow-listing to restrict data warehouse access to known corporate IP ranges. -> Screen for credentials appearing in infostealer dumps and force rotation before attackers can reuse them. -> Remember: in a shared-responsibility SaaS/cloud-provider model, tenant-side authentication hardening is the customer's responsibility, not the vendor's. Incident console: https://www.aboutiam.com/bulletins/?bulletin=snowflake_breach

Question: How do security teams respond to and mitigate a Credential-Stuffing via Password Reuse attack?
Answer: Mapped Category: Credential & Session Theft. Attack Vector: Automated Login Replay of Leaked Credential Pairs. Question: How do security teams respond to and mitigate a Kerberoasting Against Service Accounts attack?

Answer: Mapped Category: Federation & SSO Exploits. Attack Vector: Forged Cross-Tenant Token via a Compromised Federation Trust Relationship. Detailed Playbook Mitigation Steps: Strictly validate that a token's issuer claim matches the specific tenant it claims to represent — never trust an issuer to vouch for an arbitrary tenant. -> Maintain per-partner-IdP trust scoping so a compromised partner can only ever assert identities within its own delegated tenant boundary. -> Periodically audit every federated trust relationship for weak signing algorithms, stale certificates, or overly permissive issuer wildcarding. -> Require partner IdPs to meet a minimum security bar (rotated signing keys, MFA-protected admin consoles) as a condition of remaining in the federation trust chain. ## Section 4: Real-World Identity Breaches Post-Mortems Q&A

Question: What was the root cause and mitigation for the SolarWinds Golden SAML Hack breach?
Answer: Root Cause: A supply-chain backdoor gave attackers domain-admin access, and the AD FS private signing key was reachable and exportable from that vantage point with no additional hardware protection (no HSM binding).. Remediation Step: Store the AD FS token-signing key in an HSM or Azure Key Vault-backed HSM so it can never be exported to disk, rotate signing certificates regularly, and monitor for SAML assertions issued with abnormal lifetimes or claims. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=goldensaml

Question: What was the root cause and mitigation for the MFA Push Fatigue Prompt Bombing breach?
Answer: Root Cause: Legacy "just tap Approve" push MFA gives the user no context about what they are approving, so social-engineered fatigue eventually produces an approval.. Remediation Step: Enforce number-matching push MFA (a code shown on the login screen must be typed into the phone prompt), rate-limit repeated MFA challenges per user, and alert on abnormal push-approval request volume. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=pushfatigue

Question: What was the root cause and mitigation for the OAuth Wildcard Redirect Hijacks breach?
Answer: Root Cause: The authorization server validates the redirect_uri against a wildcard/prefix pattern instead of an exact registered string match.. Remediation Step: Register exact redirect URIs (RFC 6749 §3.1.2 / RFC 9700 best practice) with no wildcard matching, and require PKCE so a stolen authorization code alone cannot be exchanged for a token. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=wildcard

Question: What was the root cause and mitigation for the Okta HAR Support Ticket Cookie Theft breach?
Answer: Root Cause: Browser HAR exports capture full request/response headers, including live session cookies and bearer tokens, and were uploaded to a support system without any redaction.. Remediation Step: Redact Authorization/Cookie/Set-Cookie headers before accepting any diagnostic file upload, bind sessions to device fingerprints (DPoP/token-binding), and short-expire support-facing session tokens. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=oktahar

Question: What was the root cause and mitigation for the Entra ID Silver SAML Attack breach?
Answer: Root Cause: The relying-party application trusts a self-signed certificate whose private key is stored outside of central IdP-managed protections, with no certificate pinning against IdP-published metadata.. Remediation Step: Pin the relying party's SAML signature verification to the certificate published in the IdP's own metadata (never trust an embedded certificate from the assertion itself), and rotate app-specific signing keys on a schedule. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=silversaml

Question: What was the root cause and mitigation for the LastPass Offline Vault Cracking breach?
Answer: Root Cause: Key-derivation iteration counts were never force-upgraded for legacy accounts, leaving them orders of magnitude weaker than the modern OWASP-recommended minimum.. Remediation Step: Force-upgrade every stored credential to the OWASP-recommended PBKDF2/Argon2id parameters on next login, and never let a legacy account remain on deprecated key-derivation settings indefinitely. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=lastpass

Question: What was the root cause and mitigation for the RockYou Plaintext Password Leak breach?
Answer: Root Cause: Passwords were stored as plaintext strings instead of being hashed with a salted, slow key-derivation function.. Remediation Step: Never store raw passwords — always hash with a slow, salted algorithm (bcrypt/Argon2id), and fix the underlying SQL injection with parameterized queries. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=rockyou

Question: What was the root cause and mitigation for the Disney+ Launch-Day Credential Stuffing breach?
Answer: Root Cause: No rate-limiting or breached-password detection on login, combined with widespread password reuse across the ecosystem.. Remediation Step: Rate-limit login attempts per account/IP, screen new/changed passwords against known-breach corpora (e.g. HaveIBeenPwned k-anonymity API), and nudge users toward MFA at signup. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=disney-credential-stuffing

Question: What was the root cause and mitigation for the Colonial Pipeline Single-Factor VPN Breach breach?
Answer: Root Cause: A legacy remote-access account was never decommissioned or migrated to require MFA.. Remediation Step: Require MFA on every remote-access path without exception, inventory and decommission legacy/unused accounts, and monitor for credentials appearing in breach-dump feeds. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=colonial-pipeline

Question: What was the root cause and mitigation for the Twitter Admin Tool Social Engineering breach?
Answer: Root Cause: Overly broad internal admin-tool permissions were reachable by a wide set of support staff, with no step-up verification for sensitive account-takeover actions.. Remediation Step: Apply least-privilege and separation-of-duties to internal admin tooling, require a second approver for destructive identity actions (email/phone resets on high-value accounts), and train staff against phone-based social engineering. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=twitter-bitly-admin-tool

Question: What was the root cause and mitigation for the Capital One SSRF & Over-Privileged IAM Role breach?
Answer: Root Cause: The compromised IAM role was over-privileged relative to the workload's actual needs, and the instance metadata service (IMDSv1) had no request-header protection against SSRF.. Remediation Step: Enforce IMDSv2 (session-oriented, SSRF-resistant metadata requests) fleet-wide, apply least-privilege IAM policies scoped to exact resource ARNs, and continuously audit for SSRF in any request-proxying component. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=capitalone-ssrf

Question: What was the root cause and mitigation for the Uber GitHub-Leaked AWS Keys breach?
Answer: Root Cause: Long-lived static cloud credentials were committed directly into application source code instead of being fetched at runtime from a secrets manager.. Remediation Step: Never commit static cloud credentials to source control — use short-lived, workload-scoped identity (IAM roles, OIDC federation) fetched at runtime, enable secret-scanning on every repository, and rotate any credential ever found in git history. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=uber-github-aws-keys

Question: What was the root cause and mitigation for the Marriott/Starwood Long-Dwell Breach breach?
Answer: Root Cause: No continuous re-verification of privileged sessions or credentials; a stolen administrator credential from 2014 remained valid and undetected through a corporate acquisition and system migration.. Remediation Step: Time-box every privileged session, require periodic re-authentication/step-up for administrators, rotate credentials on a fixed schedule regardless of suspected compromise, and re-audit all inherited access during any M&A system integration. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=marriott-starwood

Question: What was the root cause and mitigation for the 0ktapus SMS Phishing Campaign breach?
Answer: Root Cause: Phishable MFA factors (OTP codes, simple push approvals) can be relayed in real time by an attacker's proxy phishing page, unlike a phishing-resistant hardware-bound factor.. Remediation Step: Migrate high-value accounts to phishing-resistant FIDO2/WebAuthn passkeys, which are cryptographically bound to the legitimate origin and cannot be relayed through a cloned page. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=0ktapus-smishing

Question: What was the root cause and mitigation for the Mailchimp Internal Tool Social Engineering breach?
Answer: Root Cause: A single compromised employee session granted broad, un-scoped read access across many unrelated customer accounts inside the internal tool.. Remediation Step: Require a linked support ticket/justification for every sensitive account lookup, log and alert on abnormal cross-account access patterns by support staff, and rotate customer API keys automatically after any suspected internal-tool compromise. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=mailchimp-internal-tool

Question: What was the root cause and mitigation for the Uber 2022 PAM Credential Discovery on a Network Share breach?
Answer: Root Cause: The organization's own PAM tool — meant to eliminate standing hardcoded credentials — had its master admin password hardcoded in a script left readable on a general-access network share.. Remediation Step: Never hardcode privileged credentials in scripts or files on shared drives — even for the PAM tool itself — and require just-in-time, approved, time-boxed elevation for any PAM administrator action, with routine scans for secrets left in file shares. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=uber-2022-pam-credential-discovery

Question: What was the root cause and mitigation for the GitHub OAuth App Token Theft (Heroku/Travis CI) breach?
Answer: Root Cause: Broadly-scoped OAuth tokens issued to third-party integrations were stored insecurely on the integration provider's side, and GitHub had no way to detect anomalous use of a token it had legitimately issued.. Remediation Step: Scope OAuth app permissions to the minimum required, encrypt tokens at rest on the integrating third party's side, rotate/expire tokens frequently, and monitor for anomalous API usage patterns tied to any given token. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=github-oauth-app-token-theft

Question: What was the root cause and mitigation for the Microsoft Storm-0558 Signing Key Forgery breach?
Answer: Root Cause: A key-scope validation bug allowed a consumer-tier signing key to be accepted as valid for enterprise-tier tokens, collapsing the intended trust boundary between the two key systems.. Remediation Step: Cryptographically separate signing key material and validation logic per trust tier (consumer vs. enterprise), never let crash dumps or diagnostics retain live key material, and require automated key-scope assertions on every token verification. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=storm-0558

Question: What was the root cause and mitigation for the Snowflake Mass Credential-Stuffing Breach breach?
Answer: Root Cause: MFA was optional rather than enforced by default, and customer accounts had long-lived static credentials with no network-based access restrictions.. Remediation Step: Enforce MFA as a platform default (not opt-in) for every account with data access, apply network policies/IP allow-listing for data-warehouse access, and rotate credentials whenever infostealer-harvested credential dumps surface. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=snowflake-credential-stuffing

Question: What was the root cause and mitigation for the MOVEit Mass Exfiltration (Cl0p) breach?
Answer: Root Cause: An unauthenticated SQL injection vulnerability let attackers bypass authentication entirely and directly manipulate the application database to plant a persistent web shell.. Remediation Step: Use parameterized queries/ORMs everywhere (never string-concatenate untrusted input into SQL), patch internet-facing file-transfer appliances immediately, and treat any managed file-transfer product as a high-value target requiring network segmentation. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=moveit-mass-exfil

Question: What was the root cause and mitigation for the NotPetya Golden Ticket Lateral Movement breach?
Answer: Root Cause: Domain controllers were reachable from standard workstations with no tiered administration model, and the krbtgt account hash — once obtained — grants effectively unlimited forged-ticket authority with no expiry enforcement.. Remediation Step: Implement a tiered administration model (Microsoft ESAE/PAW-style) so domain-admin credentials are never exposed on standard workstations, rotate the krbtgt account password on a fixed schedule, and segment networks so lateral movement cannot reach domain controllers at will. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=notpetya-golden-ticket

Question: What was the root cause and mitigation for the Change Healthcare Ransomware via No-MFA Citrix breach?
Answer: Root Cause: A single internet-facing remote-access portal was exempted from the organization's MFA policy, and that exemption alone provided the entire initial-access foothold.. Remediation Step: Enforce MFA on every remote-access surface with zero exceptions, treat any policy "exemption" as a standing audit finding requiring remediation, and monitor for anomalous authentication + lateral movement patterns even after a successful login. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=change-healthcare-no-mfa

Question: What was the root cause and mitigation for the LAPSUS$ MFA-Fatigue & SIM-Swap Chain breach?
Answer: Root Cause: Phone-number-based recovery/verification and simple push-approval MFA were both trusted as strong factors despite being remotely subvertible without any device compromise.. Remediation Step: Move privileged and contractor accounts to phishing-resistant, device-bound authenticators (FIDO2/WebAuthn) that cannot be subverted by a SIM swap or a fatigued approval tap, and require number-matching at minimum wherever passkeys are not yet deployed. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=lapsus-mfa-sim-swap

Question: What was the root cause and mitigation for the Scattered Spider Help-Desk MFA Reset breach?
Answer: Root Cause: Help-desk identity-verification procedures relied on easily-guessed or easily-researched knowledge-based facts (employee ID, manager's name) rather than a hardware-bound or out-of-band verification step.. Remediation Step: Require live video or manager-signoff verification (not knowledge-based facts alone) for any help-desk-initiated MFA or password reset, and route sensitive identity-recovery requests to a dedicated, trained identity-verification team rather than a general help desk. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=scattered-spider-helpdesk

Question: What was the root cause and mitigation for the Okta 2022 Sitel Subprocessor Breach breach?
Answer: Root Cause: A third-party subprocessor was granted standing, broad access to sensitive account-recovery tools with insufficient session isolation, monitoring, or time-boxing from the primary vendor.. Remediation Step: Grant third-party subprocessors just-in-time, time-boxed, and fully session-recorded access to any sensitive support tooling rather than standing access, and require the same identity hardening (phishing-resistant MFA, device posture checks) on subprocessor workstations as on internal ones. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=okta-sitel-subprocessor

Question: What was the root cause and mitigation for the Kerberoasting & DCSync Active Directory Attacks breach?
Answer: Root Cause: Service accounts are routinely configured with weak, never-rotated passwords, and directory-replication permissions (needed legitimately only by domain controllers) are often granted more broadly than necessary.. Remediation Step: Use Group Managed Service Accounts (gMSA) with automatically rotated, cryptographically random passwords instead of static service-account passwords, and audit/restrict "Replicating Directory Changes" permissions to only the domain controllers that legitimately need them. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=kerberoasting-dcsync

Question: What was the root cause and mitigation for the Pass-the-Hash Lateral Movement breach?
Answer: Root Cause: NTLM authentication accepts the hash itself as proof of knowledge of the password, and local administrator/service-account hashes are frequently reused identically across many machines.. Remediation Step: Deploy Local Administrator Password Solution (LAPS) so every machine has a unique, rotated local admin password, enable Windows Credential Guard to prevent hash extraction from memory, and disable NTLM fallback in favor of Kerberos wherever possible. Breach profile: https://www.aboutiam.com/wall-of-shame/?tab=breaches&lab=pass-the-hash-lateral-movement

## Section 5: Enterprise Identity Case Studies Q&A

Question: How did Netflix architect and scale its identity stack for Scaling Edge Gateway Security & mTLS Mesh?
Answer: Summary: Deconstruct Netflix’s edge architecture, utilizing Zuul API Gateway, stateless cryptographic tokens, and service-to-service mTLS mesh powered by SPIFFE/SPIRE. Core Problem: Securing thousands of decoupled microservices processing billions of daily video requests without incurring heavy database lookup latencies or relying on fragile static keys. Auth Model: Consumer Smart TVs and mobile clients authenticate via OAuth 2.0 Authorization Code Flow + PKCE. Upon validation, the Zuul edge gateway issues a stateless, encrypted token containing validated claims, which is propagated down to downstream microservices. Authz Model: Coarse-grained Authorization is validated at the Zuul Edge Gateway. Microservices implement fine-grained Attribute-Based Access Control (ABAC) using localized policy engine checks to verify resource ownership claims. Lessons Learned: Stateless tokens are essential for scaling edge APIs but require strict, short-lived lifespans.; Decoupling token validation from DB state improves fault tolerance dramatically. Case study: https://www.aboutiam.com/case-studies/?study=netflix

Question: How did Uber architect and scale its identity stack for Consumer Passwordless & FIDO2 Passkeys Integration?
Answer: Summary: Explore how Uber transitioned millions of drivers and consumers away from phishable SMS MFA toward hardware-backed FIDO2 Passkey logins. Core Problem: High volumes of driver credential-stuffing and social-engineering phishing attacks bypassing SMS/MFA prompts, leading to session takeovers and account compromises. Auth Model: Biometric passkey authentication utilizing asymmetric public-key cryptography (WebAuthn/FIDO2). Drivers generate local private/public key pairs during registration, registering only the public key to Uber servers. Authz Model: Role-Based Access Control (RBAC) maps drivers, consumers, and merchants to specific gateway permissions, validated against active session tokens on each REST API endpoint. Lessons Learned: SMS MFA is no longer secure against motivated social-engineering or SIM-swap attacks.; Passkeys provide superior security while drastically reducing driver login times (frictionless UX). Case study: https://www.aboutiam.com/case-studies/?study=uber

Question: How did Cloudflare architect and scale its identity stack for Zero Trust Access & Employee Device Posture?
Answer: Summary: Deconstruct how Cloudflare replaced corporate VPNs with a Zero Trust Access model, verifying employee device compliance, networks, and biometric status continuously. Core Problem: Securing administrative and internal corporate resources from compromise without VPN bottlenecks, enforcing continuous device-compliance checks globally. Question: What is the exploit vector and secure code fix for CVE-2016-7036 (python-jose RSA/HMAC Key-Confusion Signature Forgery)?

## Section 8: Interactive Interview Preparation Q&A

Question: [Interview Category: OAuth/OIDC] An attacker manages to intercept an authorization code in an OAuth 2.0 flow. How can you prevent them from exchanging it for an access token?
Answer: Implement PKCE (Proof Key for Code Exchange - RFC 7636). The client generates a random `code_verifier` and sends its hash (`code_challenge`) in the initial request. When exchanging the authorization code, the client must send the original `code_verifier`. The authorization server hashes it and verifies it matches the original challenge. An attacker with only the code cannot guess the verifier. Hint: Think about dynamically tying the authorization request to the token request without using a static client secret. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q1

Question: [Interview Category: Zero Trust] How do you enforce Continuous Access Evaluation (CAEP) in a system where JWT access tokens are valid for 1 hour?
Answer: Using the Shared Signals Framework (SSF) and CAEP. The Identity Provider pushes asynchronous security events (like "Session Revoked" or "Device Risk Elevated") directly to the Resource Server (API Gateway). The Gateway caches these events and immediately denies access, overriding the local JWT expiration time. Hint: If a token is valid but a security event happens (e.g., device compromised), how does the resource server know? Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q2

Question: [Interview Category: Cryptography] A developer uses the "none" algorithm in a JWT to bypass signature verification during testing, but leaves it in production. What is this attack called and how do you prevent it?
Answer: This is the "Algorithm Confusion / None Algorithm Bypass" attack. To prevent it, the JWT validation library must be hardcoded to strictly enforce an expected list of secure algorithms (e.g., `algorithms: ["RS256"]`) and reject any token presenting `alg: none`, `alg: HS256` (when expecting RS256), or unsupported algorithms. Hint: The library is blindly trusting the header of the token. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q3

Question: [Interview Category: Core IAM] What is the primary difference between Authentication (AuthN) and Authorization (AuthZ)? Provide a simple analogy.
Answer: Authentication (AuthN) verifies WHO you are. Authorization (AuthZ) determines WHAT you are allowed to do. Analogy: AuthN is presenting a valid boarding pass at the airport security checkpoint. AuthZ is the gate agent checking if your boarding pass allows you into the First Class Lounge. Hint: Identity vs Permissions. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q4

Question: [Interview Category: SAML] What is a SAML Signature Wrapping (SSW) attack, and how does a validator defend against it?
Answer: SSW abuses the mismatch between the XML node a validator cryptographically verifies and the node the application logic actually reads. An attacker copies a legitimately-signed assertion, wraps it inside a new, unsigned envelope containing forged attributes, and moves the original signed assertion to a sibling location the application ignores. Defenses: validate the signature against the exact node referenced by its own `Reference URI` (not just "a signature exists somewhere in the document"), and reject any document with unexpected/duplicate assertion IDs. Hint: The attacker doesn't forge a signature — they exploit how the XML is parsed versus how it is validated. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q5

Question: [Interview Category: PAM] Why is "Just-in-Time" (JIT) privileged access considered more secure than always-on standing admin access?
Answer: Standing admin access means a compromised credential is exploitable 24/7. JIT access grants time-boxed, approval-gated elevation only for the duration of a specific task, then automatically revokes it and rotates the credential. This shrinks the attack window from "always" to "minutes," and every elevation event is individually logged/approved, satisfying least-privilege and audit requirements. Hint: Think about the attack window and the blast radius of a compromised credential. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q6

Question: [Interview Category: Compliance] Under GDPR, what is the difference between a Data Controller and a Data Processor, and why does it matter for an IAM system logging user access?
Answer: The Data Controller determines the purposes and means of processing personal data (e.g., the company running the IAM system). The Data Processor processes data on the controller's behalf (e.g., a cloud IdP vendor). This matters for IAM audit logs because the controller is accountable for lawful basis and data subject rights (access/erasure requests), while the processor must only act on the controller's documented instructions and support those rights contractually (Art. 28 DPA). Hint: Who decides *why* data is processed vs who just executes the processing. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q7

Question: [Interview Category: Directory/Kerberos] What is a "Golden Ticket" attack in Kerberos, and why is it so hard to detect?
Answer: A Golden Ticket forges a Kerberos Ticket Granting Ticket (TGT) using the stolen KRBTGT account's password hash, granting the attacker domain-wide, arbitrary-duration admin access without ever touching a real domain controller after the initial compromise. It's hard to detect because the forged ticket is cryptographically valid — the only reliable remediation is rotating the KRBTGT password (twice, due to two-generation key retention) and hunting for anomalous ticket lifetimes/encryption types in logs. Hint: The attacker has already compromised the one account that signs every ticket. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q8

Question: [Interview Category: Cryptography] Why is bcrypt (or Argon2) preferred over SHA-256 for storing passwords, even though SHA-256 is cryptographically "stronger" in terms of collision resistance?
Answer: SHA-256 is designed to be fast — great for integrity checks, terrible for password storage, since an attacker with a GPU can compute billions of hashes per second to brute-force a leaked hash. bcrypt/Argon2 are deliberately slow, tunable ("work factor") key-derivation functions designed to make brute-forcing computationally expensive, and Argon2 additionally resists GPU/ASIC acceleration via memory-hardness. Hint: Speed is the enemy here, not strength. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q9

Question: [Interview Category: SCIM] An HR system deprovisions an employee, but they still have access to a SaaS app three days later. Where does the SCIM integration likely fail, and how would you diagnose it?
Answer: Likely causes: the SCIM DELETE/PATCH (deactivate) request returned an HTTP 429 (rate-limited) or 409 (conflict) that wasn't retried, the user's external ID mapping drifted (so the deprovision targeted the wrong/no resource), or the sync job simply hasn't run yet due to a scheduling interval. Diagnose by checking the IdP's SCIM sync logs for the specific user's external ID, verifying the last successful sync timestamp, and confirming the SP actually deactivated (not just unassigned) the account. Hint: SCIM sync is usually asynchronous and can silently queue failures. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q10

Question: [Interview Category: Zero Trust] How does the NIST SP 800-207 Zero Trust model change the traditional "castle-and-moat" network security assumption?
Answer: Castle-and-moat assumes anything inside the network perimeter is trusted. NIST SP 800-207 assumes breach and enforces per-request authorization: every access request is evaluated by a Policy Decision Point using real-time signals (identity, device posture, location, resource sensitivity) regardless of network location — there is no privileged "inside the firewall" trust zone. Hint: What happens to trust once you're already inside the firewall? Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q11

Question: [Interview Category: OAuth/OIDC] Why should a public client (like a Single Page App) never use the OAuth 2.0 Implicit Grant flow today?
Answer: The Implicit Grant returns the access token directly in the URL fragment, exposing it to browser history, referrer leaks, and any malicious script running on the page. It also has no client authentication step. Modern guidance (OAuth 2.1) removes the Implicit Grant entirely in favor of Authorization Code + PKCE, which never exposes the token in the URL and cryptographically binds the token exchange to the original request. Hint: Where does the access token end up, and who else can read it? Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q12

Question: [Interview Category: PKI] What is Certificate Revocation and why is OCSP generally preferred over CRLs for checking it in real time?
Answer: A CRL (Certificate Revocation List) is a full, periodically-published list of every revoked certificate a client must download and search. OCSP (Online Certificate Status Protocol) lets a client query a responder for the status of one specific certificate in real time, avoiding the download/parse overhead of an ever-growing list — at the cost of a live network dependency (mitigated by OCSP Stapling). Hint: Think about the size of the revocation list versus a single lookup. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q13

Question: [Interview Category: Compliance] What is Separation of Duties (SoD), and give a concrete IAM example of a SoD conflict.
Answer: Separation of Duties requires that no single individual holds enough combined access to both perform and approve/conceal a sensitive action, reducing fraud and error risk. Example: a user who can both *create a vendor* in the ERP system and *approve payments* to vendors could create a fake vendor and approve payment to themselves — an IGA access review should flag and prevent that combination of entitlements. Hint: No single person should be able to complete an entire sensitive process alone. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q14

Question: [Interview Category: Core IAM] What does "least privilege" mean in practice, and what is the most common IAM anti-pattern that violates it?
Answer: Least privilege means granting only the minimum access necessary to perform a task, for only as long as needed. The most common violation is "role accumulation" / privilege creep — an employee changes teams over the years but old entitlements are never revoked, so their access silently grows unbounded. Regular access recertification campaigns (IGA) are the standard control against this. Hint: It's not just about roles — it's about how long access lasts. Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q15

Question: [Interview Category: Directory/Kerberos] What is "Kerberoasting," and why does it specifically target service accounts?
Answer: Kerberoasting abuses the fact that any authenticated domain user can request a Kerberos service ticket (TGS) for any Service Principal Name, which is encrypted with that service account's NTLM password hash. The attacker extracts the ticket and brute-forces it offline with no further network interaction. Service accounts are targeted because they're often configured with weak, never-rotated passwords and elevated privileges. Mitigation: long random passwords (or gMSA managed accounts) and monitoring for abnormal TGS request volume. Hint: Any authenticated domain user can request a TGS for any service — what can they do with it offline? Practice online: https://www.aboutiam.com/assistant/?tab=interview&q=q16
